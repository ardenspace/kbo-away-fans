## wellrun 의 시작 브리핑이 해야 할 세 가지

1. **강제 장치 설치 단계가 phase 1 에 있는지 확인** — 있습니다. **step 1.9** 가
   spec 의 Enforcement plan 3종(registry-sync 짝 추가, no-location-upload 신설,
   firebase-import-boundary 신설)을 설치하고 wiring 합니다. 따로 더할 것이 없습니다.
2. **run preview 표를 사용자에게 보여 주기** — `plan.md` 맨 끝에 있습니다.
   25단계 중 14개가 `fresh` 이며, 멈출 가능성이 큰 자리는 아래 "무게가 실린 네
   단계"입니다.
3. **모드 선택을 사용자에게 묻고 `run.md` 를 만들기** — companion(기본, L/XL 발견 시
   멈춤) / autonomous(멈추지 않고 가장 되돌리기 쉬운 선택을 provisional 로 기록).
   사용자에게 물을 때는 질문 도구를 씁니다.

그다음 첫 단계는 **1.1 (schedule 계약 schemaVersion 2 + 앱 파서 확장)** 입니다.

## 계획의 모양

| phase | delivers | steps |
|---|---|---|
| 1 | 델타 기반 + 강제 장치 | 1.1–1.9 |
| 2 | 계정: 로그인 게이트에서 사용자 문서까지 | 2.1–2.5 |
| 3 | 5탭 골격과 좋아요 여정 | 3.1–3.4 |
| 4 | 배지: 방문 판정 → 도장 → 판 → 연출 → 못 받는 날 | 4.1–4.5 |
| 5 | 홈 개인화 마무리 (최근 5경기·현재 위치) | 5.1–5.2 |

phase 1 의 순서: 계약 v2 와 앱 파서(1.1) → 크롤 창 과거 확장(1.2) → 토큰 네 그룹
추가(1.3) → 기존 38곳 타이포 일괄 교체(1.4) → Firestore 모델·보안 규칙(1.5) →
`lib/backend/` 계층과 read-first 문서(1.6) → 카카오 커스텀 토큰 함수(1.7) →
공유 컴포넌트 7종 골격(1.8) → 강제 장치 3종 설치(1.9).

### 무게가 실린 네 단계

- **1.5 / 1.6** — 개인 데이터의 벽(보안 규칙)과 Firebase SDK 경계가 여기서 굳습니다.
  이후 단계가 전부 이 위에 쌓입니다.
- **2.1** — 기존 154개 테스트가 함께 움직입니다. 로그인 게이트가 앱의 첫 화면이 되어
  위젯 테스트마다 인증 상태를 주입해야 합니다.
- **2.2** — Blaze 전환과 예산 상한이 걸려 있어 사용자 확인이 필요합니다.
- **4.3** — 무료 할당량이 걸린 읽기 패턴입니다. 판을 열 때 사용자 문서 하나만 읽는지를
  가짜 백엔드의 읽기 호출 수로 세어 단언합니다.

## wellplan 이 내린 판단 (계획을 읽을 때 알아야 할 것)

- **verification tier 산정 기준을 한 겹 좁혔습니다.** 규칙 그대로라면 사이클 2의 거의
  모든 단계가 XL(계정·데이터 소유권) 아래에 들어가 `fresh` 가 뜻을 잃습니다. 그래서
  L/XL 결정을 **처음 실물로 굳히는** 단계에만 `fresh` 를 주고, 이미 굳은 계약을
  소비만 하는 단계는 `basic` 으로 두었습니다. 이 기준은 `plan.md` 의 Phases 표
  바로 아래에 적혀 있습니다.
- **계약 변경을 두 단계로 쪼갰습니다.** 1.1 이 스키마·검증·앱 파서·크롤러가 찍는
  버전까지 계약 표면 전부를 올리고, 1.2 가 생산자(크롤 창과 점수 매핑)를 맡습니다.
  한 단계로 묶으면 검증 게이트가 중간에 깨져 boundary test 가 자기 단계 안에서
  통과할 수 없습니다.
- **2.2 의 실기기 로그인 확인은 명령으로 만들 수 없어서** acceptance 에만 두고,
  boundary test 는 "설정 파일 없이도 기준선이 그대로"까지만 담았습니다.

## 사용자가 이번에 승인한 것

- **1.5 의 보안 규칙은 Firestore 에뮬레이터 규칙 테스트로 검증합니다.** 이 머신에
  Java 런타임이 없어서(`java -version` 실패) 그 단계가 JDK·`firebase-tools`·
  `@firebase/rules-unit-testing` 설치까지 함께 처리하고 설치 방법을 README 개발 절에
  남깁니다. 셋 다 무료이고 Firebase 요금과 무관합니다. 이 규칙 테스트는 4.2 의 도장
  쓰기에서 다시 쓰입니다.

## 오해하기 쉬운 지점

**사이클 1 문서는 정반대를 말합니다.** `cycles/01/begin.md` 에는 "계정 없이 시작",
"서버에 개인 데이터를 두지 않는다"가 그대로 남아 있고 `decisions.md` 초반에는
"백엔드 API 서버 기각"이 있습니다. 전부 사이클 2에서 뒤집혔습니다. 아카이브는
이력이라 수정하지 않습니다. 현재 정체성의 답안지는 `.wellbegun/begin.md` 입니다.

**"원정"의 뜻이 두 갈래입니다.** 홈 화면의 D-day 와 추천은 야구 용어의 원정(내 팀이
어웨이인 경기) 기준을 유지합니다. 반면 **배지는 홈·원정을 구분하지 않고** "내가 그
구장에 갔는가"를 셉니다. 이 둘을 섞으면 판이 깨집니다.

## 실행 중 계속 유효한 제약

- **비용**: Firebase Blaze 전환과 카드 등록은 피할 수 없습니다(사용자 승인함).
  무료 할당량(일 5만 읽기·2만 쓰기)은 그대로 포함되므로 **Firestore 읽기 패턴을 그
  안에 머물게 하는 것이 설계 조건**입니다. 예산 알림과 상한을 먼저 겁니다(2.2).
- **배지 판 읽기 패턴은 이미 정해졌습니다.** 사용자 문서의 칸별 요약만 읽고, 개별
  도장은 칸 상세를 열 때만 읽습니다. 도장 쓰기가 요약 갱신을 같은 트랜잭션으로 함께
  합니다.
- **애플 로그인**: Apple Developer Program(연 $99)은 사용자가 지불하기로 했습니다.
- **위치 좌표는 서버로 보내지도 저장하지도 않습니다.** 구장 근처 판정은 기기에서
  하고 결과만 올립니다. 1.9 의 `check-no-location-upload.sh` 가 이 약속을 검사로
  지킵니다.
