# wellbegun 개선 제안 — kbo-away-fans 도그푸딩 실측 기반

작성일: 2026-08-25. 이 문서는 wellbegun 0.1.0 파이프라인 전체(wellbegin → wellspec → wellplan → wellrun)를 실제 제품 하나에 끝까지 적용해 본 결과를 근거로 작성한 개선 제안입니다. 플러그인의 설계 전제를 바꾸자는 제안이 아니라, 전제를 지키면서 비용을 줄이는 제안입니다.

## 0. 도그푸딩 run 개요

- 대상: kbo-away-fans (KBO 원정 팬 앱 — Flutter + Node 콘텐츠 파이프라인 + GitHub Pages 호스팅)
- 규모: 5 phase, 19 step, companion 모드, 수정 디스패치 2회(phase 3 통합 FAIL 1건, whole-run 리뷰 REJECT 1건), 최종 whole-run 재검증 ACCEPT
- 서브에이전트 파견: 총 36회 (구현자 22, step별 fresh 검증자 9, phase 통합 검증자 6, whole-run 리뷰 2 — 수정 디스패치 포함)
- 파이프라인이 잡아낸 실제 결함: (1) 추천 목록 앱바의 팀 테마 승계 끊김 — 구현자의 자체 테스트가 전부 themeKey 없이 렌더해서 자기 블라인드 스팟 안에 있었고, phase 통합 검증자의 자작 probe가 실측으로 잡음. (2) iOS 배포 타깃 13.0 vs Firebase SDK 최소 15.0 — 어떤 step 계약에도 "릴리스 빌드를 돌려봐라"가 없어 whole-run 리뷰만 도달할 수 있었던 블로커.
- 비용 문제: conductor(메인 루프) 컨텍스트는 25%밖에 차지 않았지만, 서브에이전트 토큰 합계 약 340만으로 Claude Max($100) 5시간 리밋이 하루에 두 번 걸림.

### 토큰 실측 (서브에이전트 usage 기록 합산)

| 용도 | 호출 수 | 토큰 | 비중 |
|---|---|---|---|
| 구현자 (19 step + 수정 2회) | 22회 | 약 200만 | 60% |
| step별 fresh 검증자 | 9회 | 약 49만 | 14% |
| phase 통합 검증자 (재검증 포함) | 6회 | 약 56만 | 17% |
| whole-run 리뷰 (REJECT 1회 + ACCEPT 1회) | 2회 | 약 32만 | 9% |

추가 관찰:

- 구현자 호출당 비용이 run 후반으로 갈수록 커짐: phase 1 평균 약 6만 → phase 4~5 평균 11~13만. 코드베이스가 자라면서 read-first로 읽어야 할 것이 늘어나는 구조적 증가.
- 가장 비싼 단일 호출은 1차 whole-run 리뷰(약 20만)였는데, 유일한 진짜 블로커(iOS 빌드)를 잡았으므로 ROI는 오히려 최고였음. 절감 대상이 아님.
- 세션 리밋으로 에이전트가 3회 중단됐고, 유실·재작업 비용이 약 25~30만. 다만 run.md 디스크 앵커 덕에 재개 자체는 매번 문제없었음.

## 1. 제안: 역할별 모델 분배 — 구현자부터 낮춘다

> 대상: wellrun. 우선순위: 높음 (최대 버킷 60%를 직접 타격)

직관과 반대로 들릴 수 있지만, wellbegun에서는 계약이 빡빡할수록 구현이 기계적이 됩니다. boundary test가 계획 단계에서 미리 고정되어 있으므로 구현자의 일은 "계약을 통과시키는 일"이고, 특히 basic 티어 step(스캐폴드, 시드 데이터 입력, 온보딩 화면 같은)은 Sonnet급 모델로 충분합니다.

구체안: **step 계약의 verification tier(6항 중 5번)를 모델 선택에도 재활용**합니다.

- `basic` (S/M 결정만 접촉) → 구현자를 작은 모델로
- `fresh` (L/XL 결정 접촉) → 구현자를 큰 모델로 유지

tier는 이미 "되돌리기 등급에서 파생"되는 값이므로 새 판단 축을 추가하지 않고, 계획서에 이미 적혀 있는 값을 그대로 씁니다. 이번 run 기준 basic 티어 step이 10개(구현자 지출의 절반 안팎)였으므로, 이 항목 하나로 체감 절감 폭이 가장 큽니다.

## 2. 제안: 검증자는 낮추지 않는다 (명문화)

> 대상: wellrun. 우선순위: 높음 (절감 압박에서 지켜야 할 선을 문서로 고정)

이번 run에서 값어치를 한 두 발견(테마 승계 끊김, iOS 빌드 블로커)은 모두 검증자의 판단력에서 나왔습니다. 구현은 계약이 이끌지만 검증은 "계약 바깥에서 실패 이유를 찾는 일"이라 판단력이 곧 성능입니다. fresh 검증자·phase 통합 검증자·whole-run 리뷰는 상위 모델을 유지해야 하며, 모델 분배 기능이 생긴 이상 "검증자 다운그레이드 금지"를 스킬 문서에 명시해 두기를 권합니다. 비용 압박을 받는 conductor가 가장 먼저 깎고 싶어질 자리가 여기이기 때문입니다.

## 3. 제안: 구현자 연속(continuity) 조항 — 기본은 fresh, 조건부로 이어 쓰기

> 대상: wellrun. 우선순위: 중간 (재파악 비용 15~20% 절감 추정)

현재 구현자는 step마다 무조건 새로 뽑힙니다. 검증자 격리와 달리 이것은 원리가 아니라 실용적 기본값이며("one subagent, one context window"), 기본값으로는 옳습니다. 근거 세 가지:

1. read-first + 레지스트리 로스터가 신선한 구현자의 파악 비용을 유계로 만들어 줌 — 두 설계는 서로를 정당화하는 한 쌍.
2. 지속 구현자는 낡은 기억으로 일하게 됨 — 이번 run에서도 수정 에이전트가 3.1 산출물을 고쳤으므로, 3.1 구현자가 살아서 4.2를 맡았다면 자기 기억과 현재 코드가 어긋난 채 작업했을 것.
3. 실패 격리 — 세션 중단 3회의 피해가 각각 step 하나로 한정됐음.

다만 중간 지대가 있습니다. 세션 리밋으로 끊긴 2.3 구현자를 SendMessage로 같은 컨텍스트째 재개시켰을 때 품질 문제 없이 효율적이었다는 실측이 있고, 같은 영역의 인접 step(이번 run에서는 1.3→1.4, 2.2→2.3, 3.1→3.2 — 전부 2개짜리 쌍)이라면 파일 파악 비용(호출당 1~2만 토큰)을 아낄 수 있습니다. 구현자의 서사 승계가 검증자의 그것보다 훨씬 덜 위험한 이유는, 구현자가 "N step이 잘 돌아간다"는 가정을 안고 N+1을 지어도 **그 가정을 fresh 검증자가 독립적으로 다시 확인하기 때문**입니다.

구체안 (스킬 문구 순서까지 포함한 제안):

> 기본은 fresh. 단, 다음 조건을 모두 만족하면 conductor 재량으로 직전 구현자를 SendMessage로 이어 쓸 수 있다: (1) 직전 step이 수정 없이 PASS했고, (2) 두 step의 계약 4번 항목(읽을 로스터)이 겹치고, (3) 같은 phase 안이다. 연속은 3 step을 넘기지 않는다.

그리고 개수와 무관한 즉시 리셋 조건을 함께 명시합니다:

- 직전 step 검증이 FAIL → 수정은 무조건 fresh (기존 규칙 유지 — 검증 발견을 사실로만 받는 새 눈이어야 함)
- 영역(로스터)이 바뀜 → 이어 쓸 이득 자체가 없음
- phase 경계를 넘음 → 통합 검증이 끼어들고 그 결과로 코드가 바뀔 수 있음
- 사이에 다른 에이전트의 커밋이 끼었음 → 구현자의 기억이 낡음
- L/XL 정지 후 재개 → 기존 규칙(fresh + 기록된 결정) 유지

"기본은 fresh"를 문구의 맨 앞에 두는 것이 중요합니다. 이어 쓰기가 예외임을 구조적으로 지켜야, 토큰 압박을 받는 conductor가 과하게 이어 쓰는 쪽으로 흐르지 않습니다. 연속 3 step 상한의 근거: 구현자 하나가 step당 6만~13만 토큰을 쌓으므로 세 번째 step부터는 이전 step의 낡은 테스트 출력·중간 산출물이 죽은 무게가 되어, 절감하려다 품질을 잃는 지점이 그 근처입니다.

## 4. 제안: 검증의 구조 비용 절감 3건

> 대상: wellrun. 우선순위: (b)가 가장 높음

**(a) 회귀 확인을 conductor로 이관.** 현재 fresh 검증자마다 전체 테스트 스위트(`flutter test` 등)를 다시 돌립니다. basic 티어처럼 conductor가 boundary test·전체 스위트를 직접 실행하는 방식을 fresh 티어의 "회귀 확인" 부분에도 적용하면, 검증자는 자기만 할 수 있는 일(adversarial probe 설계·실행)에 컨텍스트를 집중할 수 있습니다. 검증자의 격리 원칙과 충돌하지 않습니다 — conductor가 전달하는 것은 여전히 "실행 명령과 그 결과"라는 사실이지 구현자의 서사가 아닙니다.

**(b) phase 통합 probe의 자산화 — 이 문서에서 가장 추천하는 항목.** 이번 run에서 phase 통합 검증자들이 매번 정교한 여정 probe(콜드 스타트 → 온보딩 → 홈 → 추천 → 긁기 → 지도, 실 HTTP 서버 포함)를 처음부터 작성하고, 검증이 끝나면 삭제했습니다. phase 2·3(FAIL 라운드와 재검증 각각)·4·5의 probe가 상당 부분 겹칩니다. 검증자에게 **"검증을 통과한 probe는 회귀 테스트로 커밋할 수 있다"**를 허용하면:

- 다음 phase 검증자와 whole-run 리뷰가 그 위에서 시작하므로 갈수록 싸짐 (현재는 갈수록 비싸짐 — phase 통합 비용이 7.4만 → 10.7만 → 10.3만 → 9.9만으로 유지·증가)
- 일회용 검증 노동이 저장소의 영구 자산(회귀 방어선)으로 바뀜
- "재검증은 항상 새 검증자"라는 원칙과도 양립 — 새 검증자는 커밋된 probe를 "이미 있는 테스트"로 실행하고, 자기 몫의 새 probe를 더 얹으면 됨

주의점 하나: "검증자는 대상 코드를 수정하지 않는다"는 현재 규칙과의 경계를 명확히 해야 합니다. 허용 범위를 "테스트 디렉터리에 신규 파일 추가만, 기존 파일 수정 금지"로 좁히면 충돌 없이 도입 가능합니다.

**(c) 서브에이전트 프롬프트의 고정부 전치.** step마다 반복되는 고정 문구(결정 처리 규칙, 되돌리기 등급 참조, 보고 형식, 마무리 규칙)를 프롬프트의 앞쪽에 동일 문자열로 배치하고 step 고유 내용(계약·참고 사실)을 뒤에 두면, 프롬프트 캐시 적중에 유리해집니다. 스킬이 디스패치 템플릿을 제공한다면 템플릿 구조만 바꾸면 되는 저비용 개선입니다.

## 5. 제안 (작은 것): 계약 간 순서 의존 검사

> 대상: wellplan. 우선순위: 낮음

이번 run에서 step 1.3·1.4의 boundary test가 `scripts/hooks/check-*.sh`의 존재를 전제했는데, 훅 설치는 step 1.6의 일이었습니다. conductor가 디스패치 시점에 "이 step에서 스크립트 파일까지 만들어라"로 계약을 보충해서 풀었지만, 계획 단계에서 잡을 수 있는 문제입니다. wellplan에 "각 step의 boundary test가 참조하는 파일·명령은 그 step 이전(또는 그 step 자신)에서 만들어져야 한다"는 자기 검사 한 줄을 추가하기를 권합니다.

## 6. 바꾸지 말아야 할 것 (실측으로 확인된 강점)

절감 논의가 과잉 최적화로 번지지 않도록, 이번 run에서 값을 한 설계를 명시해 둡니다.

1. **검증자 컨텍스트 격리** — 실제 결함 2건 모두 "구현자의 서사를 모르는 눈"이라서 잡았음. 이 원칙이 플러그인의 존재 이유이며, 위 제안들은 전부 이 원칙을 침해하지 않는 범위로 설계했음.
2. **whole-run 리뷰의 규모** — 단일 호출 최고 비용(20만)이지만 유일한 릴리스 블로커를 잡았음. 깎을 자리가 아님.
3. **foundation-first(phase 1 고정)** — run 전체에서 "일단 하드코딩" 부채가 0건. 훅이 위반 커밋을 실제로 차단함을 검증자들이 반복 확인.
4. **디스크 앵커(run.md·decisions.md·pending/)** — 세션 중단 3회를 전부 무손실로 재개. mini-ADR 누적(100줄 이상)이 후속 step의 입력으로 실제 소비됨.
5. **재검증은 항상 새 검증자** — phase 3 FAIL 후 재검증에서, 이전 발견을 모르는 새 검증자가 수정 확인에 그치지 않고 전체 여정을 다시 걸어 통과시킴. "이전 발견만 확인하는 검증자" 함정을 실제로 회피.
