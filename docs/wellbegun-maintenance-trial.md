# 유지보수 렌즈 수동 실험 규약

run 마감(2026-08-25) 이후의 일상 변경 — 당장은 디자인 테마 수정 — 에 wellbegun의 유지보수 렌즈 후보 규칙을 **스킬 없이 수동으로** 적용하고, 그 사용감을 기록하는 실험이다. 여기 쌓인 관찰이 2차 개발 진입 전 iteration 설계 세션의 입력이 된다. 실험 기간은 테마 수정 시작부터 2차 개발 진입 전까지.

## 변경마다 지키는 규칙

1. **코드 전에 등급을 매긴다.** 질문은 하나: "이 결정이 틀렸다면 되돌리는 비용이 얼마인가?" 1분 안에 끝내는 분류 동작이고, 두 등급 사이에서 망설여지면 높은 쪽을 택한다.
   - **S** — 몇 분, 파일 하나 안 (네이밍, 내부 구조, 문구)
   - **M** — 하루 미만, 파일 몇 개, 마이그레이션 없음 (컴포넌트 내부 상태, 설정 기본값)
   - **L** — 미니 프로젝트: 데이터 백필, 레이어 가로지르는 연쇄 수정 (공유 컴포넌트 API, 계약 형식)
   - **XL** — 재작성, 또는 사용자에게 보이는 파괴 (플랫폼, 데이터 소유권)
2. **S/M이면** 그대로 진행하고, `.wellbegun/decisions.md` 원장에 기존 형식으로 한 줄 ADR을 추가한다.
3. **L/XL이면** 코드 전에 멈춘다: 대안을 비교해 결정하고, `rejected:` 절을 포함한 ADR을 원장에 추가하며, 상단 L/XL 색인을 같은 커밋에서 갱신한다.
4. **registry 규칙은 run 밖에서도 유효하다.** 영역을 건드리기 전에 그 영역의 로스터(REGISTRY.md)를 읽고, 공용 요소는 재사용하거나 — 없으면 공용 폴더에 만들고 같은 커밋에서 로스터를 갱신한다.
5. **훅은 계속 그린이어야 한다.** `check-hardcoded-values.sh`, `check-registry-sync.sh`가 통과하는 상태로 커밋한다. 테마 수정은 토큰 파일(`lib/design/`)을 고치는 작업이지, 하드코드 예외를 만드는 작업이 아니다.

## 같이 굴리는 B4 실험

`.wellbegun/decisions.md` 상단에 L/XL 색인 섹션을 두었다. 원장은 시간순 추가 전용을 유지하고, L/XL 결정을 추가할 때만 색인도 함께 갱신한다. 관찰할 것: 색인 유지가 성가신가, 아니면 자연스럽게 굴러가는가.

## 관찰 항목

로그를 남길 때 특히 주목할 것들:

- 등급 매기기가 번거로웠던 순간 — 어떤 변경에서, 왜.
- mini-cycle 승격 경계 사례 — "이건 일상 변경이 아니라 작은 run으로 돌렸어야 했나?" 싶었던 변경.
- registry·훅 규칙이 conductor 없이 저절로 지켜졌는지, 깨질 뻔했는지.
- 렌즈가 실제로 잡아낸 것(코드 전에 멈춰서 이득 본 결정)과 놓친 것(등급 없이 그냥 지나간 변경).
- 색인 유지 마찰 (B4).
