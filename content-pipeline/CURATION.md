# 장소 큐레이션 워크플로 — `content-pipeline/curation/`

시범 구장(잠실)에서 확립한 워크플로. **나머지 8개 구장은 이 문서의 반복이다.**
장소 계약은 `schema/places.schema.json` 이 원본.

## 워크플로 (입력 → 검증 → 병합)

1. **입력** — `curation/<stadiumId>.json` 파일을 만든다 (구장 id 는
   `schema/common.defs.schema.json` 의 9종). 형식:

   ```json
   {
     "stadiumId": "<stadiumId>",
     "places": [ /* places.schema.json 의 place 객체들 */ ]
   }
   ```

   파일명·문서 `stadiumId`·각 장소의 `stadiumId` 는 전부 일치해야 한다
   (병합기가 강제 — 복붙으로 다른 구장 장소가 섞이는 사고 방지).

2. **검증 + 병합** — 저장소 루트에서:

   ```sh
   node content-pipeline/build-places.mjs
   ```

   `curation/*.json` 전체를 병합해 스키마 + place id 유일성 검증을 통과한
   경우에만 `data/places.json` 을 교체한다. 실패하면 기존 산출물 무변경.

3. **확인** — 병합기 로그의 `stadium_coverage` 로 구장별 커버리지를 보고,
   `coverage_below_threshold` warn 이 없는지 확인한다. 이어서
   `npm --prefix content-pipeline test` 와 `flutter test` 로 회귀를 확인한다.

## 구장별 최소 커버리지 (플랜B 성립 조건)

| 항목 | 최소 | 이유 |
|---|---|---|
| 장소 수 | 10건 | 목록이 여정을 지탱할 최소 분량 |
| 카테고리 | 3종 | 필터 칩이 의미를 갖는 최소 다양성 |
| 실내 장소 | 3건 | 우천 플랜B(실내만 필터)가 비지 않을 조건 |

미달이면 병합기가 warn 을 남긴다 (채우는 중일 수 있어 실패는 아님 —
**출시 전에는 9개 구장 전부 충족이 조건**).

## 장소 품질 규칙

- **실존만**: 실제 가게·시설을 웹으로 조사해 넣는다. 좌표는 실제 위치에
  최대한 가깝게 (구 단위 오차 허용, 임의 창작 금지). 확신이 없는 정보는
  아래 재검수 표에 등록한다.
- **샤라웃(`shoutout`)은 근거가 있을 때만**: 방송·인터뷰·구단 콘텐츠 등
  실제 출처를 짧게 적는다. 근거를 못 찾으면 `shoutout` 없이 일반 큐레이션으로
  넣는다 — 허위 출처 금지.
- **id 규약**: `<stadiumId>-<가게 슬러그>` (예: `jamsil-bunong`). id 는 문서
  전체에서 유일해야 한다 (validate 의 의미 검사가 강제).
- **`indoor`**: 우천 플랜B 필터 근거다. 애매하면(야외석 중심 등) false.
- **문구 톤**: `description` 은 원정 팬에게 말 걸듯 1~2문장, 과장 없이.
  `shoutout` 은 뱃지에 그대로 노출되므로 "누가/어디서" 가 드러나는 한 줄.

## 나머지 8개 구장 채우기 (운영 반복)

구장당 이 순서를 반복한다:

1. 조사 — "<구장/동네> 야구선수 단골 맛집", "<팀명> 선수 맛집" 등으로 샤라웃
   후보를 찾고(잡지·방송·구단 콘텐츠가 근거로 좋다), 방탈출·카페·명소로
   카테고리를 3종 이상 확보한다. 실내 3곳 이상 필수.
2. 주소·좌표 확보 — 지도 서비스에서 도로명 주소를 확인하고 좌표를 딴다.
   추정 좌표는 위 재검수 표 형식으로 이 문서에 등록한다.
3. `curation/<stadiumId>.json` 작성 → `node content-pipeline/build-places.mjs`.
4. 이 문서에 구장 현황 절(건수·카테고리·실내·샤라웃 근거·재검수 목록)을 추가.
5. 커밋 — data/places.json 과 curation 입력, 문서 갱신을 한 커밋으로.
